## I1 — valid Python function paths disable existing advanced edits

Primary location: `apps/web/src/features/planning/function-target.ts:7–15`, particularly line 12. The accepted suffix expression contains only `ts|tsx|js|jsx|mjs|cjs|mts|cts`; `.py` is rejected even when the path is the unchanged physical/effective path of an already indexed Python function.

Actual integration path and effects:

1. `PlanEditor.tsx:66–85` carries the selected function's physical identity and effective path into the editor; `PlanEditor.tsx:283–300` mounts `FunctionForm` for any function, including Python. There is no Python-specific alternate editor.
2. `FunctionForm.tsx:24–28` initializes the accepted file path from that node. Lines 41–46 call the suffix validator and leave `targetPath` undefined on rejection. Lines 67–72 then refuse submission, and line 130 disables Save whenever `targetPath` is absent. Changing only description, name, or signature does not change this result.
3. The operation helper has the same regression independently of the form. `operations.ts:67–85` unconditionally calls `retargetFunction` before creating a metadata annotation. `function-target.ts:45–46` validates before checking whether the target equals the effective path. Thus a metadata-only `editFunction` on `main.py` also throws rather than preserving that path and emitting the annotation.
4. Existing Python temporary additions are affected as well: the same form and `operations.ts:76–82` reject their legal `.py` target when editing metadata. The new file/folder ownership workflow also hardcodes the same TS/JS-only list in `features/structure/ownership.ts:26,39–50`. This is one common supported-path defect, not a separate finding.

**Concrete source-derived reproduction:** open/index a supported Python project containing `main.py` and an `entry` function; create/select a current, nonstale plan; select that real function in Advanced editing; change only its description while leaving `main.py` unchanged. The form computes `targetPath = undefined`, shows `main.py → …`, and permanently disables Save. Through the helper, `editFunction([], pythonNode, { name: pythonNode.name, filePath: "main.py", signature: ..., description: "updated intent" })` reaches the rejected suffix before the unchanged-path no-op and cannot produce the previously supported annotation. This follows directly from the frozen code; no product execution or test was performed during this review.

This is a regression from BASE0991, not a request for a new Python source writer: the original patch shows `FunctionForm` previously submitting the existing path unchanged and `editFunction` accepting same-path metadata edits without a suffix gate. `packages/core/src/validation.ts:77,108–136` still models Python and permits canonical relative `add_function` / `move_function` paths. README line 104 explicitly includes Python projects and line 108 requires editing explanations and target files. The requirements brief expressly binds preservation of existing features; the coordinator confirmed TS/JS/Python preservation remains binding. The approved FS design also allows supported source filenames or previously captured valid source-file targets (`docs/superpowers/specs/2026-10-10-fs01-design.md:49`).
