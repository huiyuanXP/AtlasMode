## 方案选择与最小边界

选择“持久分组的明确类型 + 规划中的冻结组合契约 + 已有 must_reuse”。仅写 description/annotate 虽改动少，缺少可独立编辑的顺序与入口类型，不满足票；引入通用分支编排/代码生成/运行时顺序验证超过票范围。此次 sequence 提供线性明确顺序及文本组合约定；分支和数据传递可明确写在约定中，但不伪称机器建模、执行或证明了这些文本。

已有入口 wrapper 属于长期 Knowledge。新 wrapper 在选中 Plan 内提案：产生真实的 add_function 意图及组合契约；tempId 不写入长期 FunctionGroup。实施、重新索引后用户明确选取实际函数绑定到长期 wrapper。该分离避免悬空跨规划引用和自动猜测绑定，不要求索引器、源代码 writer 或新存储 kind。

## 数据与兼容性

core 新增 `GroupComposition`：

```ts
type GroupComposition =
  | { kind: 'capability' }
  | { kind: 'sequence'; order: string[]; contract: string }
  | { kind: 'wrapper'; entryId: string };
// FunctionGroup 增加 composition?: GroupComposition; revision?: number。
// 无 composition 的旧记录 = capability；无 revision 的旧记录 = r1。
type GroupContractOperation = {
  kind: 'group_contract'; id: string; groupId: string; title: string;
  memberIds: string[];
  composition: Exclude<GroupComposition, { kind: 'capability' }>;
};
```

读归一化不改旧 JSON；旧 capability 请求、规划、批准可继续解析和按原算法核对。新客户端保存完整 draft，包括 composition，使用 `expectedRevision` 与 `expectedSnapshotId`；revision 由服务生成，创建 r1，语义变化 r+1，合法 no-op 不改时间/revision/批准。旧客户端编辑既有记录省略 composition 时保留已存类型，不能默默把新 sequence/wrapper 降回 capability。显式转回 capability 使用 `{kind:'capability'}`，并在预览中列出将删除的顺序/入口知识；取消不改数据。旧客户端改变成员导致已存高级类型不合法时返回错误，保留原记录，不能截断契约。

新限制仅作用于高级 payload，不使用新上限拒读旧 capability 的 title/ID/成员或截断既有值；超限转换需明确错误。高级 composition/contract 最多 200 个不同成员；新 ID 字段 1–200 字符，title 1–2000 非空字符，sequence.contract 0–20000 字符。旧 capability 全成员无损保留，超过新上限只能继续 capability 编辑，显示转换限制；不能截断到 200 或只转换加载的 20 项。新的严格 schema 拒绝未知字段、错误 union 混合、重复 order 与越界。memberIds 作为集合去重；sequence.order 必须是去重 memberIds 的准确排列，每成员恰好一次，二者绝不互相替代。顺序变动是语义；memberIds 单纯重排、source 标记变化与 view 布局仍沿用既有语义规则。

持久 wrapper.entryId 必须是同项目当前快照的真实 function（不接受 temp/external/ReactFlow alias/组卡 ID）。entryId 与成员集合是两种职责；入口可以显式出现在成员集合，但不自动加入、不自动排除；UI 必须清楚标记，并拒绝生成 entry→entry 的复用要求。刷新丢失绑定时仍保留原 ID/文本，显示 missing/unknown；未加载不等于消失。高级保存必须通过服务的权威快照验证，不依赖当前画布分页。

新增组 CAS 仅扩现有 POST groups 输入：`expectedRevision?:number`、`expectedSnapshotId?:string`；所有新客户端编辑要求捕获的组版本/快照，高级创建要求快照。服务在同一同步 storage.transaction 内读当前 record/项目快照，验证 project、CAS、所有成员与 entry，生成 revision，写组并统一使本项目当前规划失效。旧 capability 调用保留旧兼容行为；兼容调用也需在事务内保留最新 composition、增加语义 revision。历史批准不被修改。读取 revision 必须是正 safe integer；递增溢出 fail closed。组来源由原编辑 draft 保留，不借类型转换改变 Agent/用户来源。

group_contract 是 Plan 的真实 typed operation，记录冻结的组 id/title、全成员和显式组合，不引用实时组内容来解释历史。它不增加 CodeSnapshot node/relation、contains/member_of 事实或 parentId。只允许 sequence/wrapper；memberIds 来自已保存组的真实成员，wrapper.entryId 在契约内可以是该同一规划中的 add_function.tempId，或其 baseline/current snapshot 中真实函数。验证以当前规划操作集收集新增后再解析引用；入口/成员被 remove_function、缺失、错误种类或跨 plan/project 时阻止保存/批准。id 提供单项编辑/删除身份，不允许重复。

Planning.update 同一事务内对新增/实质修改的合同重读其源组：groupId 必须存在且归本规划项目，title/成员集合与该次源组相符；order 是这次明确规划的排列，不要求跟实时组旧 order 相同，planned wrapper 可以基于 capability/sequence 提案。已有且 payload 完全未变的合同允许保持历史冻结内容，不被当前源组重写。组语义变更后 UI 明示当前组与冻结合同差异；刷新合同是显式预览动作，不能自动传播。这里不增加一个独立 Group approval hash。

组内容比较沿用 title/description/排序去重 memberIds，并增加归一化后的 composition（capability 与旧字段缺省等价；sequence.order 保留顺序）；排除 revision 和 source。CAS 检查仍先于 no-op 判定。必须/建议是生成预览的选择，保存后实际硬要求以独立 must_reuse operations 为准；合同详情列出这些当前真实规划要求，不把一个建议标签用于掩盖其它已存在硬要求。

新增 variant 进入既有 planSchema/semanticPlanContent，旧 variant/hash 的序列化不变；不新增全局 Approval 规则，不改变已有 must_reuse 含义。重排 order 或改入口会改变当前 revision/hash；修改 group 已沿用既有保守失效，不能自动更新批准规划里的旧契约。已有历史合同与批准按其冻结 payload 阅读/验证。

## 真 UI 流程

在现有高级 GroupsPanel 内提供类型选择和完整表单，首用默认仍 capability。所有按钮实际行为与验收一一对应：

| 入口/按钮 | 必须产生的行为 |
| --- | --- |
| 类型选择、转为 sequence | 展示全成员 ID 列表及独立编号 order；无顺序旧组初始取当前保存成员次序，明确是待确认初稿，不称已执行顺序 |
| 上移/下移、组合约定、保存/取消 | 键盘与鼠标均可编辑顺序，成员加入需显式补入顺序，移除同步移除 step；保留未加载/缺失 ID，缺失阻止高级提交；取消还原持久值 |
| 转为已有 wrapper、选择入口、检查入口 | 从同项目真实函数选取；读取域 ID 上下文与原文件源码；无加载证据时显示加载/未知，不能以 alias 当函数 |
| 加入规划、建议/必须复用 | 打开捕获 project/snapshot/plan/revision 的预览，列全成员、顺序或入口、契约、拟新增操作；必须模式指定实际调用方；建议模式可不选调用方，预览明确来源和目标 |
| 规划新 wrapper | 完整入口名称/目标文件/签名/说明表单，复用 FS-01 完整路径验证和有效目标 helper；预览 add_function + wrapper group_contract；没有源字节或当前真实入口 |
| 入口内部必须复用的成员 | 独立明确勾选真实成员子集；预览逐个 entry→member 的 must_reuse，不按 memberIds 自动创建；默认无内部要求 |
| 保存到规划 / 编辑已存契约 / 删除契约 | 一次 CAS 保存全部明确操作，产生一个 revision/history；删除只删除契约，不偷偷删用户另写的关系/入口；明确列出可能残留要求，用户另行确认编辑 |
| 实施后绑定实际入口 | 重新索引后显式从真实函数选取并 CAS 保存长期 wrapper；不靠同名/path 自动迁移知识 ID |

“必须复用”：sequence 从用户所选调用方对显式选择的步骤目标产生现有 must_reuse（默认全步骤但预览逐项明确）；wrapper 对实际/该 plan 临时入口产生 caller→entry must_reuse。每条要求就是直接调用要求，界面明确说明，不把成员集合当 transitive/runtime reuse。已有完全相同要求可复用并在预览标记“已存在”，不能合并不同关系种类、删旧事实边或生成 source=target。必须模式无合法 caller 或无目标时不可保存。

“建议复用”：保存 group_contract 组合意图，不创建 must_reuse，也不借 calls/must_call 伪装成事实或硬要求。是否需要内部必须复用另由上述独立勾选决定，若有勾选，预览与按钮文案必须说明即使外部是建议仍含内部硬要求。契约的顺序/文本本身总是规划要求，不声称能静态证明。

新 wrapper 的临时入口只属于当前 Plan：取消预览不写；换项目/plan/快照/revision 令预览过期，不自动重基；删除 add_function 后保留契约并显示 INVALID_TARGET/阻止批准，或在删除预览中明确选择一起删契约，不静默修复；undo/redo 产生新服务版本；不存在/跨 plan tempId 必须拒绝。历史批准中的入口绑定使用其历史 add_function，而非另一条当前规划。重载及 owned-server 重启恢复 Plan 契约，不出现已实现标签。

## 保存、批准、验证与共享依赖

新组合预览不能调用当前会临时读取新 revision 的通用 savePlan 盲存；使用 FS-01 的捕获元组保存路径，提交 captured expectedRevision+expectedSnapshotId，既有 Planning.update 同步事务检查 current snapshot 与 plan baseline。组变化会增加该 plan revision，因此捕获之后的语义组修改同样使批量保存冲突。组保存与规划保存是两个明确用户动作，不构建跨动作补偿事务、不自动重试/批准。

未提交组表单/组合预览按既有 pending 机制阻止批准旧版本。accepted PlanDetail 是批准有效性权威；异步 response 必须检查项目/plan/导航 generation，不能覆盖另一页面、另一组或新预览。source 查看沿用 FS-01 物理域 ID/filePath 的 snapshot/generation guard；planned path 不能用于读另一真实文件。当前 source 是实时字节，不声称历史快照字节。

验证器保持原 add_function 与 add_relation/must_reuse：入口存在能提供真实路径，要求被满足需真实直接 calls 行证据；完整分析找不到为 unmet，动态/不完整/歧义为 unknown。group_contract 单独输出 unknown，说明“组合顺序、分支和数据传递需人工核对”，并列已绑定/缺失/未知的成员与入口位置证据；不能仅凭调用集合把 sequence 判 satisfied。即使 wrapper 的全部 must_reuse satisfied，也只证明列出的直接调用，不证明完整内部行为。不存在实际入口不得称 wrapper 实施完成。

FS-01 正在接线：复用有效物理/计划路径 helper、捕获元组与 source guard；layout drag、ownership drag、circle-selection 分开，组卡不可成为源码移动目标。KN-01 正在扩不可变 annotation reviewContext，POL-01 正在统一结构 mutation queue；此次沿用它们最终 API 和知识失效边界，不建立第二个审批/项目队列，不更改知识哈希范围、不把 group_contract 偷加进旧 approval 的 annotation context。Plan 自身冻结 payload 由原 plan semanticHash 覆盖。AG-02 将消费新 operation 的声明性契约，未支持时必须显式拒绝/报告 unsupported；本票不实现 source executor，也不把未知 variant 静默丢弃。

GRP-02：普通组投影仍按真实 memberIds 已加载交集；sequence 编号与入口标记是知识说明，不能用 order 合成 calls 边。planned wrapper 用现有规划函数 overlay；契约用 PlanOverview/独立详情展示，不能凭知识 group 创建假 CodeNode。持久已存在 wrapper 的入口即使不是成员或不在当前范围，也只显示绑定摘要/打开上下文，不为了卡片强行扩大事实查询。保留 fold/layout/alias true ID 与 fact 查询预算/镜像计数。
