## Chosen minimum architecture

Introduce a separate server-owned `ImplementationRun`, backed by a typed, schema-validated `settings/implementation-run:<id>` record. Keep `Plan.status` unchanged. The current SQLite migration CHECK only admits existing record kinds; namespaced settings avoid silently requiring a migration or mixing execution state into approval history.

An explicit planning-Chat action, labelled with the approved revision, starts implementation. A message such as “implement this” in ordinary planning Chat continues to have no source authority. Approval and start remain separate user actions. Start binds immutable `{projectId, planId, revision, approvalId, semanticHash, baselineSnapshotId, baselineContentHash}` plus a server-issued run id and idempotency key. Browser or model supplied `approved:true`, paths, provider, executable or credentials never confer authority.

Before starting, the UI obtains a durable implementation ticket for that exact tuple and the immutable generation-message digest. Ticket issuance has no provider or target-write effect. It sends a retained client request nonce solely to deduplicate ticket issuance; the nonce is not an authorization key. The server persists `{clientNonce, tuple, messageDigest, ticketKey, runId, expiresAt, state: issued}` with the bounded generation message in server-private run data before returning the opaque server-generated ticket key and run id. Repeating issuance with the same nonce and identical payload returns the same ticket; a changed tuple/message with that nonce is a conflict. A lost issuance acknowledgment is recovered by retrying the same nonce, never by silently creating another intent.

Start uses only the previously received ticket key and its bound project. The server transaction claims `issued -> started` once, then reruns the actual approval/source/capability preflight. Repeating start with the same key returns the existing run, including failure, cancellation or interruption, without another provider invocation/publication. A key paired with a different tuple/project is rejected. A lost start acknowledgment is recovered by retrying that key or querying the already-known run id; the UI never generates a replacement key. Unstarted expired tickets cannot start, and expired/retired nonce/key mappings retain a rejection tombstone rather than being rebound; reject new issuance at the configured record budget instead of silently evicting active or replay-sensitive records. Recovery also precedes any restart dispatch: a claimed but not terminal run is interrupted, not automatically started again.

The smallest initial vertical slice supports **new eligible UTF-8 source files in existing project directories**, with an approved `add_function` and any supported relations originating in the same new file. This can implement real source, refresh the index and map the temporary function to a real symbol. Existing-file replacement and multi-file plans are separately gated capabilities, not silently accepted or approximated. Unsupported operations return `needs_revision`/`SOURCE_WRITE_UNAVAILABLE` before provider calls or any target writes. This first slice alone does not close the entire AG-02 acceptance matrix.

Generate one bounded structured edit bundle, then stop the provider. Reuse the unchanged `createResponsesRunner` as a read-only generator with only existing read tools plus `get_approved_plan`; capture approved source context on the server and pass it as data. Its output is parsed as strict JSON by the execution bridge and is never an executable instruction. No new source-write MCP tool, no larger planning allowlist, no target-native shell/cwd, and no relaxation of native CLI flags. Responses is the first supported generation transport; native implementation stays explicitly unsupported until an independently checked transport extension. Real provider evidence remains separate from local HTTP fixtures.

The generator does not invoke the source writer. Only the server execution coordinator can apply a validated bundle after the checks below. Ordinary Chat run/message types and journals are not reused to imply source commits.

## Approval and path authorization

1. Resolve the stored project to a canonical physical root and acquire an implementation lease keyed by that root, so aliases cannot run two writers against the same checkout. Project ids retain their existing meaning; do not rewrite project or approval identities.
2. Refresh and read the actual current plan plus actual persisted approval. Require `detail.valid`, exact current revision/hash, project ownership and the pinned baseline. Refuse historical r1 approval for a current r2 draft even if `verifyPlan` still returns r1.
3. Compile an exact file allowlist from approved operations and baseline facts. `add_function` names its file; move would require source and destination; removal would use the baseline symbol file; a relation authorizes its source file, not every callee file. Unresolved/ambiguous paths and annotations grant no write authority. No directory wildcard or model-derived scope.
4. V1 accepts only new source files (`ts/tsx/js/jsx/mts/cts/mjs/cjs/py`) in existing, eligible, non-ignored directories. Deny `.git`, dependencies, generated/cache roots, configuration/auth files and secret-like paths. Do not create directories, delete files, change modes or execute project configuration. New filenames required outside the approved operations require a new user-approved revision.
5. Capture raw-byte hashes, absence for new files, path identities and bounded source context. A SHA over text after newline conversion is insufficient. Require a complete supported baseline for automatic execution; incomplete index coverage cannot be turned into permission.
6. After generation, refresh/recheck the exact approval tuple and source baseline again. Parse the entire bundle and validate every path/hash/budget before the first target write. The model cannot expand the server allowlist or supply trusted originals.

The operation allowlist is deliberately conservative. Caller/import/test files needed outside it must become visible approved scope first; do not silently add them. Byte/path authorization does not prove behavioral correctness or that every change matches the intended design; post-write verification and source diff remain required evidence.

## Writer capabilities and concurrency limits

Keep filesystem I/O in a server adapter behind a pure `SourceWriterPort` defined in core; do not add writes to `IndexerPort` or filesystem imports to core. Service owns approval/lease/run decisions, server owns transport and the actual writer. No new workspace or external dependency is assumed.

V1 must **fully stage before making any target source pathname visible**. Create an executor-owned private staging artifact on the same supported filesystem, write all bounded bytes while handling short writes, verify actual length and raw-byte hash from the artifact, flush its file handle with `fsync`/`FileHandle.sync`, and persist its private-directory entry according to the selected adapter's process-crash contract. A stage short write, EIO, cancellation, failed verification or failed flush cannot proceed to publication. Direct `wx` creation followed by writing target bytes is forbidden: it can leave a partial visible source on error/abort/crash. Do not use `exists -> writeFile('w')`, overwrite rename, copy-then-unlink, or an overwrite/truncate fallback.

Persist a prepublication intent containing the approval/run/ticket identity, canonical root and parent identities, exact target-absence expectation, the retained private stage/provenance identity, verified byte count/hash and publication-not-attempted state. After its durable acknowledgment, persist and acknowledge a `publication_attempted` fence **before invoking** the publication primitive. Failure to acknowledge either record prevents that invocation. A crash after the attempted fence but before the OS call is conservatively uncertain; do not move this fence after the OS call and misclassify a saved target as never attempted. The adapter may then publish the complete artifact through a tested **atomic no-replace** operation. A same-filesystem link-based publication with a retained private provenance anchor is an acceptable candidate only when the adapter proves the required identity/root guarantees; the target must never be exposed with partial content by this executor. Retain that private anchor until publication and journal acknowledgment are reconciled. Hash equality alone is not provenance. If the filesystem/platform cannot guarantee complete-content no-replace publication and recoverable ownership evidence, report unsupported and fail closed.

All ancestor and final path checks must reject symlinks, outside roots, unexpected identities, special files and unsupported filesystems. Capture the physical root once and recheck its identity. Reject pre-existing targets, including hardlinks; any additional link to the private stage is permitted only as the executor's recorded publication/provenance mechanism, not as a generic hardlink exemption. No target code is evaluated. After publication, inspect actual target identity/bytes, flush the target parent as required by the supported adapter, and acknowledge observed publication in the journal before cleaning the retained anchor. Any publication, flush or acknowledgment ambiguity goes through recovery below. Cancellation waits for dispatched publication and recovery/journal observations, then stops scheduling further effects.

For existing-file replacement, plain `hash -> rename` is **not an atomic compare-and-swap against unrelated editors**. `O_NOFOLLOW` on the final component alone does not secure ancestor replacement. A platform adapter must prove its root/descriptor anchoring and conflict guarantees, or fail closed. Do not sell an in-process lease or filesystem watch as a lock against arbitrary other processes. Existing-file auto-write stays disabled until the independent writer review accepts a concrete implementation and tests. Windows/macOS/network-filesystem capability is unavailable until actually exercised; do not infer write safety from AG-05's portable HTTP support.

The product trust boundary continues to exclude a malicious same-user process with unrestricted filesystem access, as README already states. Nevertheless model-controlled path traversal, pre-existing links and observed concurrent edits must be blocked. Any stronger claim about parent-swap races needs OS-specific evidence; it is a release gate, not a prompt instruction.

During bounded application, service plan/group/policy writes that could revoke the pinned approval must fail with `IMPLEMENTATION_BUSY`; retain client dirty edits. Generation permits edits, which invalidate the subsequent apply preflight. Refreshes for aliases of the same physical root must not publish a partial writer snapshot. Different physical projects remain independent.

Future multi-file application needs a per-file write-intent/commit journal and an expected evolving source state. The first own write makes the original baseline stale; never ignore arbitrary baseline changes, and never call `detail.valid` after each own write then bypass its failure. Before first write check original approval validity; while applying check pinned semantic approval plus the run's recorded expected state. Do not represent a multi-file batch or SQLite plus filesystem as one atomic transaction.

## Run lifecycle, cancellation and recovery

Ticket state precedes execution: `issued -> started`; run states are `generating -> checking -> applying -> verifying -> completed`, with terminal `cancelled`, `failed`, `needs_revision`, `interrupted`. Store pinned authority, exact scope, ticket/nonce binding, original/expected hashes, verified private staging/provenance identity, prepublication intent, publication-attempt state, observed target identity/hash/length, acknowledgment status, committed relative paths, generation status and structural report. No raw key, endpoint credentials, hidden reasoning or provider error body in public progress or receipts.

Recovery is a prerequisite to normal startup dispatch. Before allowing refresh, approval, implementation or approval-revoking metadata writes for a root, register and quarantine all roots with durable started/pending runs; aliases share that quarantine. Read-only progress may expose `recovering`, and recovery may inspect files privately, but normal refresh must not publish a new snapshot that users could approve while ownership is unresolved. Publication followed by journal ACK failure triggers the same quarantine immediately in the live process. Do not release it merely because the target hash matches.

Reconcile against the **durable prepublication record plus retained private provenance anchor** and actual target observations:

| Observation | Recovery classification and action |
| --- | --- |
| Target absent and trustworthy evidence proves publication was not attempted | `not_published`; no target publication by this run; private partial stages may be cleaned only after their ownership is proved |
| Target absent after an attempted/uncertain publication | `unknown`; it may have been published and later removed; never claim zero writes from absence alone |
| Complete target has expected length/hash and its stable identity is proved to be the retained recorded stage/anchor | `complete_owned_observed`; record the observed saved source, with run `interrupted` after crash/ACK failure, not automatically completed or replayed |
| Visible target is short/truncated or otherwise partial | `partial_observed`; record actual length/hash/identity, no own-commit or success assumption; this contradicts the executor publication invariant and keeps the root quarantined for manual reconciliation |
| Target changed after publication, or target differs from recorded provenance | `conflict`; preserve the actual file, report changed bytes/identity, never remove/overwrite/rollback it; identical bytes on a different inode/identity are still not proof of an own commit |
| Stage anchor, root/parent identity, durable intent or target ownership cannot be proved | `unknown`; report actual available evidence, retain `interrupted` and quarantine until explicit manual reconciliation |

All observations, including partial/conflict/unknown, survive in the run journal and public recovery summary; do not synthesize `completed`, `zero writes`, or a committed-path claim from a provider return, desired hash, successful start response, or an I/O error code. A complete-owned observation can release quarantine only after its evidence is durably recorded and a recovery refresh marks the original baseline stale; partial/conflict/unknown require explicit manual reconciliation before normal refresh/approval is unblocked. Never automatically resume/replay pending publication, delete a possibly edited target, or roll it back. Private cleanup must validate executor ownership and must retain evidence on uncertainty.

Cancellation before publication is attempted means no target publication by this executor, although private staging writes may exist. Once publication is dispatched, drain it and reconcile its actual effect before returning a terminal result: saved complete source is reported when proved; ambiguous ownership is `interrupted` with quarantine, not a falsely empty cancelled result. Lost responses use the same ticket/run lookup rather than reapplying.

The minimum durability claim is **process-crash recovery on the actually tested local filesystem** with flushed stage/provenance entries and committed SQLite intent/observations. Validate the effective SQLite durability mode rather than treating a returned transaction as an unconditional power-loss promise. File and required directory flushes are part of the supported capability. Sudden power loss, hardware/cache/filesystem failure, cross-filesystem publication and network filesystems are not claimed supported by process-kill fixtures. If restart shows missing/contradictory durable evidence, classify unknown and quarantine. A power-loss guarantee requires separate platform/storage proof and tests; never infer it from process-crash recovery or ordinary fixture PASS.

After a write, refresh, verify the run's **pinned approved revision**, and map temporary ids to current symbols. Existing generic `verifyPlan` can remain historical; a run cannot silently attach a different newer approval's report. UI distinguishes saved source, unmet/unknown structure and behavior `NOT_RUN`. Source tests/package scripts are not executed by this ticket's minimum executor; any later command capability needs its own authorization and sandbox design. Show changed files and focus actual symbols/differences only when the user remains on the same project/run sequence. Switching/unmounting cancels a newly acknowledged active run and preserves saved facts.

## Acceptance and stop gates

| Gate | Required evidence |
| --- | --- |
| Current approval | Unapproved draft, old approved revision, forged tuple, stale baseline, semantic/policy/group change all block writes |
| Source implementation | Real fixture creates approved source; captured bytes, SQLite journal, fresh index and mapped function agree |
| Paths | Valid foreign project/plan, traversal/absolute/encoded path, ignored/secret/config file, symlink ancestor/final, hardlink/special file and unsupported FS fail closed |
| New-file conflicts | Target appearing after generation or immediately before publication remains untouched; no replace/open-truncate fallback |
| Existing-file capability | Disabled until explicit platform/CAS review; no false concurrent-edit guarantee |
| Publication | Stage short-write/EIO/abort/flush failure never exposes target; target appearance causes no-replace failure; only complete bytes are published |
| Lifecycle | Cancel before publication = no target publication; dispatched publication drains; prepublication provider/error/budget failure = no apply; postpublication journal ACK failure/crash preserves complete/partial/conflict/unknown evidence and quarantines root |
| Recovery provenance | Crash before/after publish, ACK failure, target edits/removal, same-hash external replacement and lost private anchor never fabricate own commit, zero writes or completed; process-crash and power-loss claims stay distinct |
| Idempotency | Lost ticket ACK reuses client nonce; lost start ACK reuses server key/known run; same key or nonce with different tuple/message conflicts; restart/expiry never replays publication |
| Isolation | Physical alias lease blocks overlapping writer; unrelated project runs proceed; no ordinary/direct planning Chat gains writer/approval access |
| UI | Actual approve -> explicit Chat implement -> saved file -> index/verify/focus; source != draft; switching project does not steal focus |
| Reporting | Historical verification, structural satisfied, behavioral NOT_RUN and real-provider/fixture results are visibly distinct |
| Full ticket | Supported source-edit/multi-file capability and the whole AG-02 ticket matrix need implementation/review evidence; new-file slice is PARTIAL |

Stop before product edits until main grants the shared file window and independent high review accepts this design. Stop before enabling a writer when a filesystem safety claim remains unproven. Stop and keep PARTIAL if only fixtures/builds pass or unsupported required operations remain. Do not edit AG-05's frozen checkpoint, AG-02 ticket/global docs, or target repositories during this design phase.

## Primary filesystem reference checked

[Node.js 24 fs documentation](https://nodejs.org/docs/latest-v24.x/api/fs.html) documents exclusive `wx` creation, warns of check-before-open races and notes that exclusive flags may not work on network filesystems. It also documents that [writeFile](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromiseswritefilefile-data-options) uses multiple internal writes and abort is best-effort with some bytes possibly written. Therefore exclusive target creation is not complete-content publication; full private staging and a tested atomic no-replace publication adapter are mandatory. These APIs do not establish repository-wide transactional CAS or a power-loss guarantee.
