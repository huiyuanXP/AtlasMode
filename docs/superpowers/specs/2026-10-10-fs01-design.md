## Ticket and observed baseline before implementation

[FS-01](../../tickets/FS-01.md) is TODO/P1, depends on completed UI-03, and requires: distinguish ownership changes from layout drag; dragging into a directory completes a filename and previews the full target path; planning only; correct explicit version approval and verification. README's operation semantics distinguish moving a card from retargeting a planned function to a file/folder. Function groups remain many-to-many knowledge references and do not confer physical ownership.

Current reusable pieces:

- [Operation](../../../packages/core/src/model.ts) and [schema/validation](../../../packages/core/src/validation.ts) support `add_function.filePath` and `move_function {nodeId,filePath}`. There is **no `move_file`**, folder move, rename-file or actual source-write operation. Moving a file/folder/group card is out of this ticket's initial scope.
- [FunctionForm](../../../apps/web/src/features/planning/FunctionForm.tsx) already has a complete target-file text field and old -> new preview inside advanced editing. [editFunction](../../../apps/web/src/features/planning/operations.ts) edits an addition in place or appends a move for an indexed function. There is no drop-target/filename workflow.
- [Canvas](../../../apps/web/src/features/graph/Canvas.tsx) drag-stop updates ordinary `view.positions` or project/root-isolated funnel offsets. It has no ownership mode/drop callback. [projection](../../../apps/web/src/features/graph/projection.ts) preserves fact node paths and displays planned move annotations.
- [Workspace](../../../apps/web/src/app/workspace.ts) saves plans through expectedRevision, versioned undo/redo and sequence-aware focus. `savePlan` reads the current revision when invoked; a preview captured earlier cannot call it blindly with stale operations and the newer current revision.
- [Planning.update](../../../packages/service/src/planning.ts) currently checks only expectedRevision. Refresh publishes a new project snapshot without incrementing the plan revision; a stale S0/r1 client can therefore save r2 after S1 publication. Independent review reproduced that acceptance in memory. FS-01 needs an atomic server snapshot precondition, not only a local tuple check.
- [Breadcrumbs/path](../../../apps/web/src/features/navigation/path.ts) binds planned paths to actual operation ids, not invented indexed file ids. Existing [navigation](../../../apps/server/src/navigation-query.ts) returns root/children from one captured snapshot, with snapshotId/budget/truncation. Missing planned paths use the existing allowMissing path; no filesystem directory enumeration is needed.
- `approvePlan` refreshes source and saves the actual revision/hash/baseline. `verifyPlan` checks historical approved source structure. A planned function move is not a performed source move. [IDX-04](../../tickets/IDX-04.md) covers explicit rename/move identity migration and remains a separate ticket.

Actual in-memory observation on VM2, using current compiled core and the source UI helper, without product/source writes, build or model calls:

The schema validates a repository-relative path shape but cannot establish that bare `dest` names a file. ## Chosen scope and interaction

Keep the default **Layout** behavior unchanged. Add a visible, text-labelled **Plan ownership** interaction beside existing graph controls, with a persistent status explaining that it edits a draft and never moves source. Enable only for a selected, non-stale plan and eligible function; disable while project/plan/knowledge writes, dirty plan metadata or circle-selection are active, explaining what must be finished. Do not silently discard group selection or dirty edits. Switching projects/plans, snapshot/revision changes and unmount cancel the local gesture/preview; toggling off cancels without saving.

Ownership mode includes a visible **Structure targets** tray with current-project breadcrumb and exact file/folder drop cards, not just a new mode button. It loads bounded captured-snapshot children through the existing scope API into an independent target-tray controller, so browsing targets does not replace the graph/funnel or move the source card. Distinguish loaded facts from paths derived solely from current plan operations; show truncation, missing and loading states. Never fabricate a directory from a guessed filesystem path or show a sampled list as the full repository tree. Matching loaded Canvas file/folder cards can use the same drop handler; group containers/mirrors and functions are not ownership targets.

Initial gesture implementation uses native HTML drag/drop on an eligible function card in ownership mode, with React Flow's layout dragging disabled for that gesture and `nodrag`/`nopan` interaction guards. It renders a transient drag image/target highlight without persisting any graph position or funnel offset. The same preview is accessible via selecting the function and activating a target card with keyboard/touch; this alternative does not replace actual pointer-drag acceptance. Root-controlled interactions must be exercised in the compiled browser before declaring it integrated. If native drag and React Flow conflict, fix the event boundary rather than synthesizing a backend mutation and calling it a drag.

Eligibility is domain identity, not React Flow `parentId`: a temporary function present in the selected plan, or an actual function in its current baseline/snapshot. Removed, unresolved/external, unloaded/unproven, file/folder/group objects and cross-project payloads cannot start ownership. A group's mirrored function can refer only to its actual member id; dragging the group does not retarget all members. Source ids and operation ids remain unchanged by FS-01.

## Drop -> complete filename -> preview -> draft save

Capture immutable local `OwnershipIntent` at drag start/target choice: projectId, snapshotId, planId, revision, source domain id, effective current path, target kind/id/canonical path, and a local gesture nonce. Drag data is a locator for that local captured intent, never authority to submit arbitrary operations; external files/URLs/text, a stale nonce and a legal foreign project/node/plan tuple are rejected.

- **File target:** show exact target file path plus fact/planned badge. The preview uses that complete canonical path; no extra basename is appended.
- **Folder target:** open a compact filename prompt, prefilled with the basename of the function's effective current file when available. The user explicitly accepts or edits the filename. If no filename is known, keep it blank; do not infer a source filename from a function name. The root folder `.` plus `feature.ts` produces `feature.ts`, not `./feature.ts`.
- The filename field accepts a single nonempty filename segment, never a directory/path. Reject slash/backslash, `.`, `..`, NUL/control characters, absolute/drive/UNC/URL notation and separator-only values; preserve the selected folder prefix. Require a supported source-file suffix for this workflow, or a previously captured valid source-file target. Display incompatible language/path constraints as actionable issues, without an unverified conversion claim.
- Canonicalize the final repository-relative path using the public core normalizer, but reject filename traversal before joining; do not silently turn a malicious filename into a different directory. No directory-only `filePath`, root-as-file or automatic recursive scope.
- Show full **current physical path**, **current planned target if different**, and **new planned target** with directory breadcrumb, function identity, revision and fact/new-planned-file status. Describe the action as “Add target change to plan”; this button does not approve or implement source.
- Cancel/Esc/outside drop/invalid target has no plan or layout save. While filename/preview is open, block accidental approval of the old revision using the existing dirty/pending affordance. Only explicit preview save sends a semantic mutation.

The preview's complete path must be the exact accepted path subsequently shown in PlanOverview, graph change text, advanced FunctionForm and planned breadcrumb. A same-name `index.ts` in another directory stays a different target; do not use basename as identity.

## Operation, revision and history contract

Shared pure `effectiveFunctionPath` and `retargetFunction` helpers in `features/planning/function-target.ts` receive plan operations, actual baseline identity/path and a canonical full target. Structure ownership and advanced PlanEditor/editFunction must both use these helpers; no path-edit entry may keep the old append-only move logic. Keeping the helper in planning avoids a planning-to-structure dependency cycle. Retargeting changes only ownership intent for that function:

- Temporary function: update its `add_function.filePath`, preserving tempId/name/signature/description/language/relations. Do not append a second move on top of the addition. Normalize any existing moves of this same temporary id into the addition's effective final path when this explicit save is accepted.
- Indexed function: derive the effective current target from the last applicable move, or its actual baseline path. Replace/coalesce only this function's move entries into one `move_function` at a deterministic existing slot; preserve all unrelated operations and authored annotations. Moving back to its baseline path removes that function's move intent. A same effective target is a no-op with no new revision/history entry.
- Do not call the generic function-edit helper with synthetic name/signature/description values, which could add accidental annotations. Do not persist a new file node, contains edge or changed fact parentId.

For legacy/imported duplicate moves, the last applicable move is the effective target until an explicit edit to that function coalesces its moves. For a temporary addition, its last legacy move overrides the addition's path for display; explicit retarget folds that effective target into the addition and removes only that id's moves. Preview, PlanEditor/FunctionForm, workspace focus, graph change text, PlanOverview and planned breadcrumb must resolve this same effective path, while keeping the physical baseline path separately. Projection should show one effective ownership change per function rather than contradictory intermediate targets. Verification's existing last-move interpretation remains consistent without an IDX-04 or core Operation change.

Advanced editing composes the shared retarget result with its existing name/signature/description annotation behavior. Preserve existing authored annotations and unrelated operations exactly; ownership-only editing does not create annotations. A same-target ownership edit has no new revision; a same-target advanced edit may still save intentional metadata/annotation changes. Form values bind to accepted project/plan/revision/domain id/effective path, rather than only `key=node.id`: a clean form updates when the accepted target changes, while dirty input is retained and marked outdated, blocks stale submit and requires explicit reload/discard. Never overwrite dirty text through an effect or silently remount it. Ownership mode remains blocked while that form is dirty.

Workspace's explicit ownership-save entry checks that project/snapshot/plan/revision and source identity still match the captured intent, then sends `api.updatePlan` with **both captured expectedRevision and expectedSnapshotId**. The new ownership API wrapper requires the full tuple at the type/call boundary; it cannot omit the snapshot or reread newer values. Advanced path edits use the same snapshot-bound save contract. On conflict reread current server state, preserve the uncommitted filename/path for comparison, mark the preview/form expired and require an explicit new preview; never auto-retry/merge/reapprove. In-flight replies obey current project and navigation generation and cannot steal newer focus.

### Atomic server snapshot precondition

Extend the strict PUT plan route, WorkspaceService.updatePlan input and Planning.update input/allowed keys with optional `expectedSnapshotId` for existing clients. Validate it as the existing nonempty id shape, not an arbitrary truthy string. Omission preserves legacy update behavior; this compatibility does **not** promise snapshot-race rejection for old callers. All new ownership and advanced target-path saves must supply it. Plan id resolves the authoritative project; the request cannot choose another project's snapshot or change the plan's project/baseline. No preflight scope request substitutes for the write precondition.

Within **the existing synchronous Planning.update storage transaction**, reread the plan, then call the existing snapshot resolver with `current.projectId`; that resolver rereads the projects record and its current snapshot from the same storage instance. Check expectedRevision and, when the snapshot field is present, (1) current snapshot id equals expectedSnapshotId and (2) the plan baseline id/contentHash still equal that current snapshot. Reject id mismatch with existing `SNAPSHOT_CHANGED`/HTTP 409, stale baseline with `BASELINE_CONFLICT`/409 and revision mismatch with `REVISION_CONFLICT`/409, before any plan put. A client supplying S1 for a plan still based on S0 cannot bypass the baseline check. Foreign/nonexistent snapshot strings fail the same current-project check. Successful parse, plan put and returned detail use this same synchronous transaction; no await, cached summary or check outside the transaction enters the critical path.

This is the same DB mutation boundary used by refresh publication, not an independent ownership queue. Evidence: WorkspaceService.storeSnapshot already writes the snapshot record and project.snapshotId inside `this.storage.transaction`; Planning.update uses that identical injected storage, and SQLiteStorage.transaction runs better-sqlite3's synchronous DB transaction and rejects async callbacks/thenables. With one server storage/connection, event-loop callbacks cannot publish a snapshot between this transaction's check and put. A refresh indexer scan may await outside that boundary: if S1 publication commits first, the S0 update fails; if the S0 update commits first, it was valid at that linearization point and later S1 legitimately makes it stale. FS-01 does not claim a snapshot promise against unindexed live disk changes or guarantee rejection merely because a scan has started.

No new queue/coordinator is needed for this bounded synchronous CAS. POL-01/KN-01 may introduce a shared project mutation coordinator for approval/policy whole use cases; main must coordinate those same WorkspaceService/Planning callers and preserve this DB precondition. Do not instantiate a second ownership queue and call it the refresh lock. If implementation adds any awaited work between check and put or moves refresh publication to another authority, stop and redesign that shared boundary with main. Prove the two commit orderings using barrier-controlled IndexerPort fixtures and actual SQLite transactions, plus HTTP/client/browser coverage; MemoryStorage alone is insufficient evidence of DB atomicity.

On success use the accepted server PlanDetail to commit semantic history and normal focus. Revision increases and any prior approval becomes invalid; old approval history remains unchanged. Undo/redo also creates server revisions and restores ownership operations, not source files. Layout/view/theme and funnel offsets do not enter semantic history or invalidate approval. Validation continues through the existing service/core directory-policy checks; warnings/unknowns are not silently converted to success.

## Factual source, planned navigation and verification

Keep captured fact `CodeNode.filePath` and contains relationships immutable. Display ownership intent as a planning overlay and expose the full new target in planned navigation. Existing-function source reads must resolve the actual function context by domain id and accept its physical path only when its returned snapshotId matches the captured current-project snapshot. Keep that physical path separately from effective planned target; never use a rewritten preview path to read unrelated destination source. New temporary functions/new planned files have no actual source; show that state rather than requesting invented file ids or pretending an existing destination's bytes implement the temporary function.

Capture project/snapshot/selection id and request generation before context/source requests; check them before issuing the source request and again before applying either response, including the returned physical filePath. A new selection, project switch, refresh or newer request cancels/invalidates the old result. On identity/snapshot mismatch, missing file, read failure or unexpected response path, clear/refuse the source panel and show a stale/unavailable/read error; never fall back to planned destination bytes. The current source API returns **live disk bytes**, with no snapshot-content hash or historical provenance check. Snapshot binding here authenticates the selected function's identity/path, not byte equality to old snapshot contents. Label the content as current source and do not claim historical/snapshot-matching bytes; unchanged local snapshot does not detect every external filesystem edit. No historical source storage, hash protocol or indexer contract expansion is included in this ticket.

Reuse plannedScopeIds/navigation for target folders/files. If the target already exists, its physical contents and pending incoming/moved functions need separate fact/planned presentation; include the actual operation ids in target focus without inventing containment facts. If it is missing, the planned breadcrumb/folder projection remains tied to operations. Target-tray navigation and planned scope focus must not manufacture an indexed file id. Reference source identity can be fetched through existing bounded function context when not loaded.

User approval remains the existing explicit action for the current revision/hash/baseline after filename/preview save. FS-01 cannot approve through a drop or emit `approved=true`. Structural verification remains pinned to a real historical approved revision. With unchanged source, an approved move must be reported `unmet`/`unknown`, not “source moved”; an added function in a missing file is likewise unimplemented. Explicit approved moves can support bounded verification binding at the intended path; do not persist general identity remapping or migrate group/annotation references by similarity—IDX-04 owns that later decision.

## Acceptance matrix and boundaries

| Scenario | Required behavior and evidence |
| --- | --- |
| Layout drag | Real pointer drag changes only view/funnel positions; plan revision/hash/approval and source bytes unchanged, including across file/folder cards |
| Ownership drag | Real function card -> visible file/folder target produces a preview and exact accepted operation; no view/offset source mutation |
| Directory completion | Blank/invalid filename blocks save; accepted filename retains exact folder; preview and all accepted UI paths agree |
| Identity/scope | Same-name files differ by full path; valid foreign ids, stale payloads, group/file/folder drags and external drop data are rejected |
| Effective operation | Ownership -> advanced -> ownership, advanced -> ownership, temp add plus legacy moves, last-effective display, no-op, return-to-baseline and undo/redo agree; annotations/unrelated operations survive; clean form follows same-id accepted path and dirty text is retained/expired |
| Version race | S0/rN request after same-project S1 publication is rejected server-side without rN+1/operations/approval write or UI history/focus commit; stale-baseline S1 and foreign snapshot fail; legacy omission stays compatible; update-before-publication may succeed then become stale; other-project refresh is independent |
| Approval | Layout keeps approval; target-path save invalidates it; explicit reapproval stores exact new revision/hash/baseline |
| Source/navigation | Fact context id/path is snapshot-bound; original-path live-byte request and response generations are checked; source is labelled current bytes, never historic hash-proven content; mismatch/read failure/late reply refuses display; existing target shows physical and planned contexts separately |
| Verification | Approved but unimplemented target is unmet/unknown with real paths; no draft verification masquerades as current authorization or completed source |
| Regression | Real 55x30 drag, map 1600/1900 zero-overlap, zoom/pan/Esc, group collapse and circle-selection, breadcrumbs and semantic undo/redo survive |
| Reporting | No native file move, source execution, identity migration or fixture-as-real-provider claim; unit success/mode button alone cannot mark FS-01 DONE |

This design authorizes no `mv`, write, directory creation or source executor call, even for approved plans. AG-02 source implementation and IDX-04 identity migration remain separate. Full/browser gates and independent implementation review are required before ticket closeout. An unsupported interaction/platform must be reported honestly; do not reduce pointer assertions to DOM event injection.
